The Change API also leaves its endpoints, bodies and several refusals undeclared. Twelve medium findings are mostly unfixed divergence points between the stories that will be written from this spine.

## Findings

### 1. [high] A Change email cannot carry the Manage link that §7 requires

- **Location:** AD-28 Issue ("returns the raw token to its caller only to build the email link. The raw token exists afterwards only in the Outbox"); AD-12 Links; AD-29 Email.
- **Evidence:** PRD §7 row "Confirmation of a Change (FR-26, FR-33) | Booker | What changed, the new Window and Seats, **the Manage link**". FR-26: "The original Booking keeps its reference and link". FR-25: "Only a hash of it is stored". After issue, `services` holds only `token_hash`, and the browser has dropped the fragment, so no code path can put the existing link into a Change email. Stories will diverge in three ways:
  - (a) re-issue the token, which revokes the link in the original email and breaks "keeps its … link";
  - (b) scrape the link out of the Outbox body, which retention clears;
  - (c) omit the link, which breaks §7.
- **Fix:** Lisa decides one option, and the spine records it in AD-28/AD-29:
  - recommended: "A Change email does not repeat the Manage link; it says the link in the booking confirmation still works", plus a one-line PRD §7 edit;
  - alternative: "every Change re-issues the Booking's Manage token (`manage.issue`), the Change email carries the new link, and the acting session's grant moves to the new token", plus a PRD FR-26 note that the link is replaced.
  - Storing the token reversibly is not an option, because FR-25 requires hash-only storage.

### 2. [high] The Change API contract is incomplete: endpoints, bodies and refusals for invalid Changes

- **Location:** AD-16 Code table; AD-28 Access; AD-29; AD-31 FR-33 cancel.
- **Evidence:** Only `POST /api/manage/{reference}/cancel {remedy}` is named. Seat move, partial move, Voucher-instead-of-Seats and Whole-sauna move have no path or body. No code is declared for requests that are well-shaped but invalid against the re-read Booking:
  - Seats to move or give up greater than the Booking's current Seats (likely after two tabs or a prior Change);
  - a target Window equal to the current one;
  - a Whole-sauna move to the same Window and Sauna;
  - `/cancel` on a Seat booking (with `remedy: "voucher"` it passes every store CHECK in AD-29 and reaches the FR-27 state through a second path with a different history `action`);
  - a Seat endpoint called on a Whole-sauna booking, and the reverse.

  AD-16 says 422 is only for shape errors, so these must be 409s. Without declared codes, each story picks its own (`invalid_input`, `rule_refused`, 404 …), which is exactly the "one refusal with two codes" divergence that AD-16 exists to prevent.
- **Fix:** In AD-28/AD-29, name the Change endpoints and bodies:
  - `POST …/move {window_id, seats}` for a Seat booking, and `{window_id, sauna_id}` for a Whole-sauna booking;
  - `POST …/voucher {seats}`;
  - `POST …/cancel {remedy}`, Whole-sauna only.

  In AD-16, add one code `409 change_invalid` with fact `reason` (`seats_exceed`, `same_target`, `wrong_kind`). In AD-29's order of checks, place it after `booking_cancelled` and before `cutoff_passed`.

### 3. [medium] History `action` vocabulary vs request action, and the remedy stored twice

- **Location:** AD-29 History and Cancellation columns; AD-9 Changes; AD-31 Prevents.
- **Evidence:**
  - `booking_changes.action` is `move | split | voucher | cancel`, but AD-29 does not say which action an all-Seats Voucher writes. AD-29 says the Booking is "cancelled with `guest` and `voucher`", so it could be `voucher` or `cancel`.
  - AD-9 refuses a repeat whose Change "differs in … action" from the request, but a `move` request becomes a `split` row when it moves only some Seats. The comparison therefore needs a mapping that nobody has defined.
  - The remedy is stored in both `booking_changes.remedy` and `bookings.cancel_remedy`, while AD-31's "Prevents" claims "the FR-33 choice stored in different places".
  - It is also unstated whether the later Remedy page choice (FR-42) writes a history row.
- **Fix:** In AD-29, state these rules:
  - "`action` is the request's action (`move`, `voucher`, `cancel`); a split is a `move` row with `new_booking_id` set." Alternatively, keep `split` and define AD-9's mapping.
  - "an all-Seats Voucher writes `action = 'voucher'` and sets the cancellation columns".
  - Drop `booking_changes.remedy`, because `bookings.cancel_remedy` is the one place. Otherwise, add a CHECK that it is set only for `cancel` and equals the Booking's column.

### 4. [medium] The Manage page cannot know the Cutoff without the browser clock

- **Location:** AD-16 Time facts; AD-4 Clock; AD-28 Access.
- **Evidence:** EXPERIENCE.md: "after the Cutoff the Manage page shows the Booking and refuses every Change with the reason". FR-26 and FR-33: "After the Cutoff, every Change is refused with an explanation". AD-16 lists only `already_started`, `horizon_end` and `horizon_days` as server time facts, and AD-4 forbids the browser clock. One story will gate the Change buttons in the SPA with `Date.now()`, while another will show them and rely on `409 cutoff_passed`.
- **Fix:** In AD-16 Time facts, add: "the Manage Booking response carries `change_allowed` (from `change_allowed(booking_id)`) and `cutoff_at`; the SPA never compares times." The AD-23 serializer gains these two fields on `/api/manage/` responses only.

### 5. [medium] Which Voucher issues write `payments` rows, and what `refund()` assumes

- **Location:** AD-13 Payments; AD-29 Voucher instead of Seats and Value; AD-30 Issue; AD-31; Deferred "Refund of a split Seat booking".
- **Evidence:**
  - AD-13 says `payments` records "how the value was funded **and returned**". AD-31 writes a `refund`/`voucher` row inside `refund()`. For a Voucher issued for given-up Seats (FR-27) or as the FR-33 `voucher` remedy, the spine says only that `booking_changes.voucher_id` points to it. One story will add a `refund`/`voucher` payments row there, another will not.
  - After a split or a partial give-up, `total_ore` is recomputed but the `payments` rows are unchanged. The split-off Booking has `total_ore > 0` and no payments at all.
  - AD-31's `refund()` "refunds the whole `total_ore`" by reading the charges, which is only correct when the charges sum to `total_ore`. Deferred relies on this never happening for Seat bookings in v1, but nothing enforces it.
- **Fix:** In AD-13/AD-29, add these rules:
  - "`payments` holds charges and the rows written by `refund()` only. A Voucher issued for given-up Seats or as a cancel remedy is recorded only through `booking_changes.voucher_id`."
  - "a split writes no `payments` rows in v1".

  In AD-31, add: "`refund()` raises (500) unless the Booking's charges sum to `total_ore`", so the deferred split case fails loudly instead of refunding the wrong amount.

### 6. [medium] One email or two when a Change issues a Voucher

- **Location:** AD-29 Email; AD-30 Issue; AD-12 Guest read ("Each Change returns its emails").
- **Evidence:** PRD §7 lists a separate "Voucher (FR-27, FR-28, FR-42) | Code, value, expiry" email next to "Confirmation of a Change". The "Whole-sauna … cancellation" email also contains "refund or Voucher". EXPERIENCE Flow 4 shows one email "with her Voucher code". The spine does not say whether FR-27 and an FR-33 cancel with `voucher` send one email or two. The answer changes the response shape, the AD-9 rebuild, the e2e tests and HT-4 counts.
- **Fix:** In AD-29 Email, add: "a Change that issues a Voucher sends one email: the Change confirmation, with a Voucher block (code, value, expiry date) from one `content/` or `services` template. A refund cancel names the Simulated refund." Alternatively, decide on two emails and say so.

### 7. [medium] Sliding grants (and sessions) write on GET, against AD-4 "Reads never write"

- **Location:** AD-28 Grant ("30 minutes, sliding on each use"); AD-8 Lifetimes ("sliding"); AD-4 Reads never write ("GET endpoints never write, with one exception").
- **Evidence:** Every `GET /api/manage/{reference}/` would update `manage_grants.expires_at` (and `sessions`). AD-4 names `ensure_generated()` as the only write a GET may make. A story author has to break one AD or the other. The pre-existing AD-8 sliding has the same tension, and AD-28 doubles it.
- **Fix:** In AD-4 Reads never write, add a second exception: "the touch of the caller's own `sessions` and `manage_grants` expiry, which locks no Window". Alternatively, slide only on POST. State also that the grant check runs in its own short transaction before the Change's `db.run`, and that a revocation between the two is accepted.

### 8. [medium] `/api/manage/*` without a session: AD-8 says 401, AD-28 says 404

- **Location:** AD-8 Creation ("A Guest write without a session gets `401 no_session`", and the SPA then calls `POST /api/session`); AD-28 Access ("answers `404 not_found` otherwise").
- **Evidence:** A Change POST after the session has expired fits both rules. If the answer is 401, the SPA's AD-8 recovery creates a fresh session without a grant, and the next call returns 404. If the answer is 404, AD-8 is broken.
- **Fix:** In AD-28 Access, add: "the Manage router answers `404 not_found` with or without a session; AD-8's `401 no_session` applies to the booking flow only."

### 9. [medium] AD-26 was not updated for §4.8: Change rules unnamed and a stale "pending" clause

- **Location:** AD-26 Machine and Cancellations; Conventions Tests.
- **Evidence:**
  - FR-31 requires the model test to apply "Changes (including partial moves)". AD-26 names only §4.13 items as later rules.
  - It says cancellation rules and C3/C4 are "marked pending" until §4.8 exists. Since 2026-11-19 §4.8 is built before §4.9, which creates the machine, so the clause is stale.
  - A cross-Window move needs at least two Windows in the machine. AD-26 says only that "Windows lie far from every time edge".
- **Fix:** In AD-26, add: "The §4.9 story that creates the machine includes §4.8's move (full and partial) and Voucher rules and FR-33 cancel/move as `@rule`s over at least two Windows." Delete the "pending" sentence.

### 10. [medium] `BP_HTTPS` default "on" reaches Core stories built before FR-24

- **Location:** AD-8 Storage (`Secure` whenever `BP_HTTPS` is on); AD-12 Links; AD-22 (`BP_HTTPS` default on); PRD §10.1 order (Core, then HTTPS).
- **Evidence:** The Core skeleton stories will be written from this spine and built first. Read literally, they create `BP_HTTPS` with default on, so the cookie is `Secure` and links use `https://`, while the server still listens on plain HTTP. httpx's cookie jar does not send `Secure` cookies to `http://127.0.0.1`, so the Core's API tests lose their session.
- **Fix:** In AD-22, add a build-order line: "Until the FR-24 story merges, there is no `BP_HTTPS` and the platform behaves as with it off. That story adds the variable with default on, the TLS listener, the redirect listener and the test-fixture switch in one PR."

### 11. [medium] How `dev` turns HTTPS off, and where dev links point

- **Location:** AD-27 Environments; AD-22; Structural Seed (dev row).
- **Evidence:**
  - AD-22 makes `config.py` the only reader of `BP_HTTPS` (default on). AD-27 says `booking-platform dev` "runs one HTTP listener", but not whether `dev` forces the flag off. If it does not, dev sends HSTS over HTTP, sets `Secure` cookies and builds `https://localhost:8443` links.
  - `--reload` re-imports `config` in a child process, so an in-process override is lost.
  - With the flag off, the default base URL is `http://localhost:8000`, but in dev the SPA is served by Vite on `:5173`. Manage links in dev emails then open a stale or missing `frontend/dist`.
- **Fix:** In AD-27 Environments, add: "`dev` sets `BP_HTTPS=0` and, unless already set, `BP_BASE_URL=http://localhost:5173` in `os.environ` before starting uvicorn with `--reload`."

### 12. [medium] The test server launch bypasses `main()`, and port selection is not decided

- **Location:** Structural Seed test row; AD-27 Tests; existing `tests/conftest.py` (starts `sys.executable -m uvicorn booking_platform.app:app --port <free>` over `http://`).
- **Evidence:** The existing fixture never calls `main()`, so after FR-24 it would run without `tls.py`, without TLS and without the redirect listener, and HT-1 could not be tested. The spine says the test server is `uv run booking-platform` with its own `BP_CERT_DIR`, but not that both `BP_HTTPS_PORT` and `BP_HTTP_PORT` are free ports. With the defaults, the test run's redirect listener collides with a running dev server on `:8000`.
- **Fix:** In AD-27 Tests, add: "The fixture starts the `booking-platform` entry point (`main()`) with free ports in `BP_HTTPS_PORT` and `BP_HTTP_PORT`, `BP_BASE_URL=https://127.0.0.1:<port>` and its own `BP_CERT_DIR`. It waits for `/api/health` over TLS. The slice fixture is reshaped to this under AD-21."

### 13. [medium] Lifecycle of the two listeners is undecided

- **Location:** AD-27 Listeners.
- **Evidence:** uvicorn 0.54.0 `Server.serve()` wraps itself in `capture_signals()`, which installs process-wide handlers and re-raises captured signals on exit (verified in `.venv/Lib/site-packages/uvicorn/server.py`). With two servers under `asyncio.gather`, Ctrl+C reaches the second server, which then re-raises to the first. The process may end with a `KeyboardInterrupt` traceback. A bind failure of one listener (`:8000` already used by dev) ends that server with `sys.exit(1)` inside its task. The spine does not say whether the other listener keeps running, and stories will differ.
- **Fix:** In AD-27 Listeners, add: "`main()` starts both servers. If either fails to start or stops, `main()` sets `should_exit` on the other and exits non-zero. Ctrl+C stops both cleanly. A test starts the platform with the HTTP port taken and expects a non-zero exit."

### 14. [medium] Lifecycle of the Change idempotency key

- **Location:** AD-9 Changes ("made when the confirming step opens and kept in `sessionStorage` as `draft:change:<reference>`").
- **Evidence:** There is one slot per reference. The spine does not say when the key is cleared. A Guest who gives up 1 Seat and then, in the same tab, moves another Seat could reuse the stored key, and AD-9 refuses a key whose Change differs with `409 invalid_key`. AD-9 also says that after `invalid_key` the SPA never makes a new key on its own, so the Guest is stuck. The booking flow states "until the booking is paid", and the Change flow has no equivalent.
- **Fix:** In AD-9 Changes, add: "The key is removed on success and when the Guest leaves the confirming step. Opening a confirming step with no stored key makes a new one. A reload of the same confirming step reuses it."

### 15. [low] Certificate regeneration rules are ambiguous

- **Location:** AD-27 Certificate.
- **Evidence:** "If any is missing … it creates them", yet "An existing CA is reused". The spine does not cover these cases:
  - `ca.pem` present but `ca-key.pem` missing;
  - the CA's own validity (if it is 365 days like the leaf, a leaf renewed at day 340 outlives its CA);
  - the key type;
  - the extensions that browsers require for an imported CA: BasicConstraints CA, KeyUsage keyCertSign, and on the leaf SAN and EKU serverAuth.
- **Fix:** In AD-27 Certificate, add:
  - "If `ca.pem` or `ca-key.pem` is missing, both the CA and the leaf are created. Otherwise only a missing or expiring leaf is re-issued."
  - "The CA is valid 10 years and the leaf 365 days, never past the CA."
  - "Keys are ECDSA P-256. The CA has BasicConstraints CA=true and KeyUsage keyCertSign; the leaf has SAN and EKU serverAuth."

### 16. [low] Voucher expiry instant vs the date in the email

- **Location:** AD-30 Issue (`app_now() + 1 year`); FR-27 ("its expiry date").
- **Evidence:** The email shows a date, but the Voucher stops working at the issue's clock time on that date. A Guest who uses it later that day is refused.
- **Fix:** In AD-30, add: "`expires_at` is the end of the Venue date one year after issue (`venue_date + 1 year + 1 day` at 00:00 `venue_tz`), and the email shows that date."

### 17. [low] Where Voucher refusals sit relative to other refusals and shape validation

- **Location:** AD-30 Spend; AD-16 Status codes ("every rule judged against the store or the clock … is a 409 from `services` after the lock"); AD-4 Clock.
- **Evidence:**
  - AD-30 refuses expired codes "before the lock". That is a clock rule judged before the lock, against the wording of AD-4 and AD-16. The authoritative judgement is the post-lock `UPDATE`, but the order against `outside_horizon`, `deadline_passed` and `no_seat_free` is unstated.
  - A malformed code (wrong length or characters) could be a Pydantic 422 or a 409 `voucher_invalid`. FR-28 wants one message.
- **Fix:** In AD-30, add:
  - "The pre-lock check is advisory and may refuse only with `voucher_invalid`. It comes after the AD-24 order and before capacity."
  - "The schema accepts any string up to 32 characters. Anything that does not normalise to 16 Crockford characters is `voucher_invalid`."

### 18. [low] Cancellation CHECKs leave two holes

- **Location:** AD-29 Cancellation columns.
- **Evidence:** The CHECK allows `cancel_cause = 'guest'` with `cancel_remedy` NULL, but a Guest cancellation always carries a choice. The store also does not stop `UPDATE window_id/seats` on a cancelled row; only `services` checks `booking_cancelled`.
- **Fix:** In AD-29, add these store rules:
  - "`cancel_cause = 'guest'` requires `cancel_remedy IS NOT NULL`";
  - the BEFORE UPDATE trigger also refuses changes of `window_id`, `seats` and `sauna_id` on a cancelled row, as a named constraint (AD-1), which gives a 500.

### 19. [low] Grant uniqueness and expiry after a move

- **Location:** AD-28 Open and Grant.
- **Evidence:** "inserts `manage_grants(…)`" on every open creates duplicate rows when a link is reopened. `expires_at` is fixed "never past the end of the Booking's Window" at insert. After a move to an earlier Window, the grant can outlive the new Window, against FR-25 "shows the Booking until its Window ends".
- **Fix:** In AD-28, add:
  - "`UNIQUE (session_id, token_id)`, and open upserts";
  - "validity is one SQL predicate, `manage_grant_valid(session_id, booking_id)`, that joins the token's validity (unrevoked, `app_now()` < end of the current Window) with `expires_at`".

### 20. [low] The `access_tokens` shape does not fit the later purposes that AD-8 routes to it

- **Location:** AD-8 Link tokens; AD-28 Storage.
- **Evidence:** `access_tokens(…, booking_id, …)` and the validity rule "before the end of the Booking's Window" are specific to Manage tokens. A Remedy token lasts 30 days, even past the Window (addendum A table), and account and reset tokens have no Booking. A later story would have to reshape a merged table (AD-15).
- **Fix:** In AD-28 Storage, add: "`booking_id` is nullable (and `account_id` is added later). Validity is decided per `purpose` in `services.manage`, with Manage = AD-28 Validity."

### 21. [low] Wording conflicts with earlier ADs on routes and session creation

### 22. [low] Split-off Booking fields are underspecified

### 23. [low] The Whole-sauna move target list needs `ignore_booking`

### 24. [low] The creation key is compared against a Booking that a Change may have mutated

- **Location:** AD-9 Same request.

- **Fix:** In AD-9, add: "`idempotency_keys` stores the request's `kind`, `window_id`, `seats` and `sauna_id` (ids and integers only), and the comparison uses them."

### 25. [low] README notes needed for HSTS on `localhost`

- **Location:** AD-27 README.

- **Fix:** In AD-27 README, add both effects in one sentence each, with the remedy: wait an hour, or clear the HSTS entry for `localhost`.
